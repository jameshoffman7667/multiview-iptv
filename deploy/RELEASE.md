# Release v0.14.0
Update: later                    (now | later; now only when James said "build, push and update" for this release)
Image: mybadreligon/multiview-iptv:0.14.0   (also 0.14 and latest; built by the push-to-main release workflow, run https://github.com/jameshoffman7667/multiview-iptv/actions/runs/43350273584, all four jobs succeeded)
Short: Add Auto quality that adapts to the buffer
Long: Auto quality starts a channel on its SD version with a short cushion, steps up while the buffer stays healthy and down when it drains or stalls, swapping streams without a gap. Opt-in per channel or in Settings.
Release commit: 76ced61 on main        Tag pushed from authoring session: no (the workflow created v0.14.0 with gh release create --target; release page has iptv-multiview.apk, 5.8 MB)
Type: minor
Port: 1234 (host = container; PORT=1234 in the image)   Exception: none. The register's target for iptv-multiview is 8043; not moved by this release.
Public hostname: unchanged by this release (see the homelab reference)        Needs Caddy route: no
New or changed env vars: none. Compose (only the image tag changes), .env.example and data format: unchanged. No manual step. New API: GET /api/quality-options?p=&sid= (login; viewers only for channels shared with them). New browser setting autoQ (default off), stored per device.
Data: /data (accounts, providers, views, settings, fantasy.json and fantasy.key; small), /recordings (REC_DIR), /rewind (REWIND_DIR); the entrypoint chowns them to uid 1000 at start. Migration: none; Auto quality keeps its state in the browser only.
Resources: idle RAM and CPU not measured for this release. New: while Auto switches a stream, a tile holds a second provider connection for a few seconds (up to 15 s) and the browser decodes two streams briefly; a tile on Auto may run a 480p transcode (TRANSCODE_MAX, default 2) only when its buffer keeps draining and the server has a GPU encoder. Bursty: ffmpeg for the shared screen / published streams (COMPOSE_MAX, default 2), recordings; RING_MB (default 32 per open channel) and the rewind buffer on disk. Compose limits (cpus) are already set on the server.
Healthcheck: unchanged. GET /healthz on $PORT -> 200 {"status":"ok","version":"0.14.0"} (JSON, no login, nothing private); compose test: wget -qO- http://127.0.0.1:$${PORT}/healthz | grep -q '\"status\":\"ok\"' || exit 1 (see deploy/compose.yaml for the exact YAML), interval 30s, timeout 5s, retries 3, start_period 30s. On vm101 use: wget -S -qO- http://127.0.0.1:1234/healthz (no curl there).
Verify after deploy:
  1. docker inspect shows "healthy" within about a minute and the logs are clean (no stack traces).
  2. wget -S -qO- http://127.0.0.1:1234/healthz returns {"status":"ok","version":"0.14.0"} with Content-Type application/json and the security headers.
  3. Open a channel, tap the screen, arrow, Quality: "Auto (adaptive...)" and "Standard" are listed. Choose Auto on a channel whose provider has an SD version: it starts within a few seconds on SD (label AUTO SD) and, after the buffer has stayed at 10 s or more for 20 s, switches to the chosen quality (AUTO FULL) with no black gap.
  4. Settings > Diagnostics (admins) lists AUTO-<step> for the screen and its last switches with the reason (buffer over 10 s, buffer under 5 s, stall, or skipped).
PWA: manifest, icons and install unchanged; service worker cache is mv-shell-0.14.0 (changes with the version). Layout: the Quality menu gained one entry; checked by the UI tests only (the sandbox browser cannot play MPEG-TS). Cloudflare Access bypass for /manifest.webmanifest, /sw.js and /icons/*: needed (state done/not done is on the server side).
Docker build: not run locally (no Docker in the authoring session); CI ran npm test, built and pushed the image and compiled the Android APK (all four jobs succeeded). The step logic, the swap and the skipped switch were tested in a browser with a stand-in player and a hand-driven clock; the 480p step was only tested as unavailable (no GPU in the sandbox). Not tested against a real stream, a real provider limit or the Android app.
Rollback: previous image tag 0.13.0 (pin whatever tag was running before this update); data restore needed? no
Known issues: the thresholds (10 s up for 20 s, under 5 s not growing for 10 s down, 60 s lock-out, 3 s start cushion) are first guesses, fixed in public/app.js. The slow-play (0.95x) that builds the cushion is slightly audible. Auto only helps where a provider has an SD version or the server has a GPU; the 0.13.0 diagnostics show whether the problem is the provider. One UI test ("admin turns logins on, publishes...") fails in the sandbox browser run since 0.9.0 (CI does not run the browser suite).
Backup tier: small/critical (include /data in Tier 1; no SQLite, JSON files, stop during copy to be safe). /recordings and /rewind are bulk (SnapRAID only; the rewind buffer is cleared at start).
